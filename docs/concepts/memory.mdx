MobKit has two memory-adjacent surfaces:

- `mobkit/memory/*` is an operational assertion and conflict ledger used by routing/gating flows. The current gateway adapter health-checks an Elephant endpoint and persists local JSON state, but query semantics are exact filters over stored assertions.
- `agent_memory` is optional identity-first agent memory injection. It is keyed by stable `AgentIdentity`, stored by realm, and injected into `AgentBuildDraft.additional_instructions` during create/resume/materialize.

## Architecture

The memory subsystem connects to a running Elephant instance via HTTP. Configuration is provided through `ElephantMemoryBackendConfig`:

```rust
ElephantMemoryBackendConfig {
    endpoint: "http://localhost:3000",
    state_path: "/var/mobkit/memory",
}
```

| Field | Type | Description |
|-------|------|-------------|
| `endpoint` | `String` | Elephant HTTP API base URL |
| `state_path` | `String` | Local JSON state file used by the Elephant-backed adapter |

The `ElephantMemoryStoreAdapter` handles connection health checks, request serialization, and error mapping.

When using the Python or TypeScript SDK through the stock `rpc_gateway`, configure Elephant with `memory.elephant(endpoint)` and enable `.persistent_state(path)`. The gateway derives the adapter state file as `<persistent_state>/elephant-memory-state.json`. Gateway `memory_config` currently supports only `backend: "elephant"` and `endpoint`; fields such as `stores`, `space_id`, and `collection` are rejected at init so unsupported configuration does not become a silent no-op.

## Indexing

Index content into Elephant with a `MemoryIndexRequest`:

```rust
MemoryIndexRequest {
    content: "The quarterly report shows 15% revenue growth.",
    source_id: "report-q4-2024",
    metadata: json!({ "domain": "finance", "quarter": "Q4" }),
}
```

The current MobKit runtime stores a canonical assertion locally and persists it when the memory backend is configured.

## Querying

Query memory with a `MemoryQueryRequest`:

```rust
MemoryQueryRequest {
    entity: Some("identity:ops".to_string()),
    topic: Some("deployment".to_string()),
    store: Some("knowledge_graph".to_string()),
}
```

The current MobKit runtime filters stored assertions and conflict signals by `entity`, `topic`, and `store`. Semantic/vector search should be supplied by a provider or upstream Meerkat memory surface rather than assumed from this RPC.

## Agent memory injection

Gateway users can enable identity-first injection with:

```typescript
MobKit.builder()
  .persistentState(".mobkit/state")
  .rosterProvider(appRosterProvider)
  .agentMemory({
    realm: "default",
    selection: "contextual",
    maxEntries: 8,
  })
```

By default, the bundled provider writes markdown under `<persistent_state>/agent-memory/<realm>/<identity>.md`. Records are inspectable and are injected as a quoted observation block for the matching durable identity. Reads are bounded to recent file tails, writes are capped, contextual recall receives the raw turn or RPC `query_text`, ignores common stopwords, scores matching records, and size-caps injected records; malformed records are skipped rather than promoted into runtime context. This keeps MobKit as a build-time and per-turn injector/projector; durable memory authority can be replaced by a custom `AgentMemoryProvider`.

Apps write identity-scoped agent memory explicitly through `mobkit/agent_memory/remember` or the TypeScript `handle.rememberAgentMemory(...)` helper, read it through `mobkit/agent_memory/recall` or `handle.recallAgentMemory(...)`, and delete individual records through `mobkit/agent_memory/forget` or `handle.forgetAgentMemory(...)`. A newly written record is available to the next identity-first send for that identity, and is also injected when the identity is materialized, resumed, respawned, or reset. Custom providers receive both raw `query_text` and normalized `query_terms` so they can implement stronger retrieval without changing MobKit runtime authority.

Agent memory is identity-scoped rather than session-scoped. A session respawn or identity reset does not delete stored memory; apps that need privacy reset semantics can call `mobkit/agent_memory/forget` for specific records or use a provider that clears memory as part of the app's identity lifecycle.

## Conflict detection

Elephant's truth maintenance system tracks conflicting assertions. When multiple sources make competing claims about the same fact, MobKit's gating subsystem can check for conflicts before approving an action via the `memory.conflict_read` MCP tool.

A `MemoryConflictSignal` indicates:
- Which assertions conflict
- The source of each competing claim
- The current truth slot resolution

This integrates with [gating](/concepts/gating) to prevent agents from acting on contested information.

## Health checks

The memory adapter performs TCP-level health checks against the Elephant endpoint before dispatching requests. The health check:

1. Resolves the endpoint hostname
2. Opens a TCP connection with `ELEPHANT_HEALTHCHECK_TIMEOUT`
3. Sends an HTTP GET to `/v1/health`
4. Verifies a 2xx status response

Failed health checks produce `ElephantMemoryStoreError::ExternalCallFailed` with diagnostic details.

## Memory store info

The `MemoryStoreInfo` struct provides introspection into the memory backend:

```rust
MemoryStoreInfo {
    endpoint: "http://localhost:3000",
    state_path: "/var/mobkit/memory",
    healthy: true,
}
```

This is available through the RPC API for monitoring and diagnostics.
