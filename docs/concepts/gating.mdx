Gating is a policy service owned by the MobKit runtime. A caller submits an action, actor, and risk tier. The runtime evaluates that request, records the result, and may create a pending approval entry.

<Warning>
Gating does not perform the proposed action. The caller must enforce the returned `outcome` before it invokes delivery, changes state, or performs another side effect.
</Warning>

There is no gating module or gating MCP tool. The runtime implements the evaluate, pending, decide, and audit contracts directly.

## Risk tiers

`GatingRiskTier` is serialized in snake case as `r0` through `r3`:

| Tier | Default outcome | Runtime behavior |
|------|-----------------|------------------|
| `r0` | `allowed` | Allow immediately and write an `evaluated` audit entry |
| `r1` | `allowed` | Allow immediately and write an `evaluated` audit entry |
| `r2` | `allowed_with_audit` | Allow with consequence-mode audit unless conflict handling falls back to `safe_draft` |
| `r3` | `pending_approval` | Create a pending entry unless conflict handling falls back to `safe_draft` |

For `r2` and `r3`, memory-conflict policy can override the default. It returns `safe_draft` when the referenced memory is conflicted, required conflict context is missing while conflicts exist, or the memory conflict lookup fails.

## Evaluation contract

The evaluate request has this wire shape:

```json
{
  "action": "send_customer_update",
  "actor_id": "agent-lead",
  "risk_tier": "r3",
  "rationale": "The customer requested an update",
  "requested_approver": "human-reviewer",
  "approval_recipient": "review-queue",
  "approval_channel": "notification",
  "approval_timeout_ms": 60000,
  "entity": "customer:42",
  "topic": "outbound_status"
}
```

Only `action`, `actor_id`, and `risk_tier` are required. MobKit mints the `action_id`. A `GatingEvaluateResult` returns:

- `action_id`, `action`, `actor_id`, and the effective `risk_tier`
- one of `allowed`, `allowed_with_audit`, `pending_approval`, or `safe_draft` in `outcome`
- `pending_id` and `pending_ref` when approval is pending
- `fallback_reason` when conflict policy forced `safe_draft`

<Note>
When the stdio `rpc_gateway` loads an `actions` map from `runtime_options.gating_config_path`, the configured tier for a matching action is authoritative. It replaces a caller-supplied `risk_tier` before evaluation.
</Note>

## Pending approval

An `r3` evaluation creates a `GatingPendingEntry` with its `pending_id`, its `pending_ref`, the action and actor identity, optional requested approver and notification fields, and `created_at_ms` and `deadline_at_ms` timestamps.

If both `approval_recipient` and `approval_channel` are present, the runtime attempts to route and send a `gating_approval_request` through the loaded router and delivery modules. The request payload carries both `pending_id` and `pending_ref`, and its idempotency key is `gating-approval-<pending_ref>`. A missing module or failed notification is recorded in the `pending_created` audit detail. It does not prevent the pending entry from being created.

Approval timeouts default to 60 seconds and are clamped to the runtime limits. Expiry is refreshed lazily when another gating operation evaluates, lists pending entries, decides, or reads the audit log. An expired entry is removed and recorded as:

```json
{
  "event_type": "timeout_fallback",
  "outcome": "safe_draft",
  "detail": {
    "fallback": "safe_draft",
    "reason": "approval_timeout"
  }
}
```

## Pending refs

Each gating owner has a random incarnation, minted when the owner is built. `pending_id` (`gate-pending-000002`) is a display ID drawn from the owner's sequence. An owner that starts without restored state starts that sequence again, so the next request it mints can reuse the display ID of a request the replaced owner issued.

`pending_ref` identifies one request across owners. On the wire it is the opaque string `gpr1.<incarnation>.<seq>`, where the incarnation is 32 lowercase hex characters and the sequence is canonical decimal:

```json
"gpr1.4f9c2e0b7d1a4c3e8b5f6a7d9e0c1b2a.2"
```

Treat the ref as opaque. Echo it verbatim from the pending entry or evaluate result. Do not trim, rebuild, or compare its parts. Escalations return the successor's ref as `next_pending_ref`. Audit entries carry `pending_ref` exactly when they carry `pending_id`.

A host that persists gating state with `gating_state_snapshot` and `restore_gating_state` persists the incarnation too, so refs issued before a restart still resolve after it. Snapshots are version 2. A version 1 snapshot, which predates incarnations, restores under a fresh incarnation, so no ref the old owner could have issued resolves against the restored owner.

## Decisions

Resolve a pending entry by its ref:

```json
{
  "pending_ref": "gpr1.4f9c2e0b7d1a4c3e8b5f6a7d9e0c1b2a.2",
  "approver_id": "human-reviewer",
  "decision": "approve",
  "reason": "Reviewed against the customer request"
}
```

| Decision | Outcome | Audit event |
|----------|---------|-------------|
| `approve` | `allowed` | `approval_decided` |
| `reject` | `safe_draft` | `rejection_decided` |
| `escalate` | `pending_approval` | `escalation_decided` and a `pending_created` entry for the successor |

Approval by the original `actor_id` is rejected. When `requested_approver` is set, every decision must come from that approver. A refused authorization leaves the request pending, in its original queue position. Escalation creates a successor pending entry, clears the requested approver, preserves the original deadline, and returns its ID and ref in `next_pending_id` and `next_pending_ref`.

### Stale decisions

A decision that does not name a request pending in this owner is refused as a stale decision. It resolves nothing, writes no audit entry, and notifies no resolution observer. The JSON-RPC error has code `-32602` and typed data:

```json
{ "kind": "stale_pending_decision", "reason": "other_incarnation" }
```

| Reason | Meaning |
|--------|---------|
| `malformed` | The request carried no canonical `pending_ref`. This includes a request that names only the legacy `pending_id`. |
| `unknown` | The ref names this owner but a request it never issued. |
| `other_incarnation` | A different owner issued the ref, such as the runtime this one replaced. |
| `resolved` | The request was issued here and is no longer pending: it was decided, timed out, or evicted. |

Treat the reason set as open. On a stale decision, refresh the pending list instead of retrying. The TypeScript and Python SDKs raise `StalePendingDecisionError` with the reason.

## Audit records

`GatingAuditEntry` contains:

```rust
pub struct GatingAuditEntry {
    pub audit_id: String,
    pub timestamp_ms: u64,
    pub event_type: String,
    pub action_id: String,
    pub pending_id: Option<String>,
    pub pending_ref: Option<PendingRef>,
    pub actor_id: String,
    pub risk_tier: GatingRiskTier,
    pub outcome: GatingOutcome,
    pub detail: serde_json::Value,
}
```

The current runtime writes these event types:

- `evaluated`
- `conflict_blocked`
- `memory_conflict_lookup_failed`
- `pending_created`
- `approval_decided`
- `rejection_decided`
- `escalation_decided`
- `timeout_fallback`

The audit log and pending queue are bounded runtime collections. They are not the unified event stream.

## Memory conflict integration

For `r2` and `r3`, the runtime checks the supplied `entity` and `topic` against memory conflicts. If the `memory` module is loaded, that core MCP boundary must provide the `memory.conflict_read` tool. Without a loaded memory module, the runtime uses its in-process conflict ledger.

The memory steward's gated quarantine promotions wait on a gating request. The steward stores each promotion under its `pending_ref` and resolves it only when a resolution names that ref, so a later owner's request that reuses the display ID never commits or discards it.
